# 卦象关系图知识库（graph KB）实施方案

## 一、背景判断

现有冻结分支 `feat/panorama-analyzer` 落后 main 87 个提交，其核心设计是**让 Agent 手写 Markdown 全景图谱**，与 main 后来确立的铁律 13（检测收敛到脚本、禁止 AI 手动识别）路线相反——这是它冻结的深层原因。你的想法比它进一步：要**可维护的图数据 + 能传给审查子代理的对照基线**，原分支两者都没有（无图、无脚本、无审查闭环）。

已确认的调研事实（决定实现方式）：
- 排盘脚本目前精确算好：节点属性、四类格局超边（三合/三会/六合/六冲）、独发独静、游魂归魂。
- 约 70% 的边是**零覆盖**：生克方向、刑、害、变爻与本爻关系（回头生克/化进退墓绝）、暗动日破月破、旺衰、用神角色。
- 缺三张必要表（脚本内不存在、只在文档里）：十二长生（`dong-bian-fa-ze.md` §九）、三刑/六害（`di-zhi-relations.md` §五/§六）、化进退（`dong-bian-fa-ze.md` §三）。
- **陷阱**：静爻也会填 `bian_yao`，建图必须先按 `dong` 门控，否则会凭空造出 4 条不存在的变爻边。

## 二、分支策略

- 从 main 新建 `feat/graph-kb`。旧的 `feat/panorama-analyzer` 保持冻结不动。
- 在 `BRANCH-POLICY.md` 记录：新分支完成后，旧全景分支可退役删除，`feat/graph-kb` 更名为 `feat/panorama-analyzer`（承接「全景扫描」名号）。
- 因为新方案与十步法兼容，完成后可正常走 PR 进 main（不受「panorama 不得合入 main」限制）。

## 四、图构建器设计

**输出两个文件，都在卦例目录内（铁律 12）**：`graph_data.json`（机读权威，审查方用）+ `关系图谱.md`（紧凑人读版，主流程引用用）。

**节点**：6 主卦爻 / 动爻的变爻（`dong` 门控）/ 伏神 / 月建 / 日辰 / 太岁（从 `ganzhi.year` 取地支）。

**每节点状态**：旬空（拆成 `day`/`month` 布尔）、月破、日破、暗动、旺相休囚死、十二长生（变爻）、入墓（日墓/月墓/化墓）。

**边**：
- 生克边（含方向）
- 动变边：回头生 / 回头克 / 化出我生者 / 化出我克者 / 比和 + 化进退 + 化空破墓绝
- 地支关系边：六合 / 六冲 / 刑 / 害（覆盖变爻、伏神、日月，比 `patterns` 更宽）
- 飞伏边：五态（飞来生伏 / 伏去生飞 / 飞来克伏 / 伏去克飞 / 飞伏比和）
- 日月边：临 / 生 / 克 / 冲 / 合 / 入墓

**超边**：三合 / 三会（补 `members`，标注变爻伏神参与）；`patterns` 原样透传作格局判定权威。

**用神层**：intent→六亲映射（感情/失物/天气给多候选）；定位明现/两现/不现（→伏神）；按候选各算一套原神/忌神/仇神。

**关键设计——每条边带 `basis` 字段**记录推导输入（五行对/地支对/月令）。图若算错可一路溯源到具体规则，不会变成不可查的黑盒。

## 五、SKILL.md 集成（增量接入，不重写第二~七步）

1. **铁律 18·图数据权威（爻际关系）**：爻际关系（生克/合冲刑害/动变性质/空破墓绝）以 `graph_data.json` 为准；与 `patterns` 分工不重叠（格局仍以 patterns 为唯一权威，铁律 13 不变）；图若发现 patterns 未覆盖的关系，标为「图扩展」并在报告说明，**不得据此推翻 patterns 的格局判定**。图如确有问题 → 修脚本重跑，**不允许步骤内就地绕过**（让 bug 集中暴露而非散落）。
2. **第零步新增子步 8「生成关系图」**（在读取 JSON 并重命名目录之后）：调用 `build_graph.py`；强制输出块增「关系图」段（节点/边数、逐爻动变性质、用神候选、格局超边）；检查点增「图文件已生成、构建器退出码为 0」。
3. **第三步**：动变分析行须注明引用图数据；检查点补一条。
4. **文末「强制触发条件表」**：进入第八步一行追加图文件。

## 六、第八步审查改动

- prompt「输入文件」增第 5 项 `graph_data.json`（沿用「缺文件判 A 项缺失，不臆测」语义）。
- 新增**审查项目 E·图数据一致性**（缺查即审查无效）：
  1. 步骤 2/3/6 声称的爻际关系是否都能在图数据中找到对应边/状态？找不到 → 判「无图依据」，Agent 臆造或图缺漏；
  2. 图标定的非空格局/动变性质，步骤 3/7 是否全覆盖？漏项判漏判；
  3. 步骤表述与图矛盾（图说回头生、报告写回头克）→ 判矛盾；
  4. **可用 Bash 重跑 `build_graph.py` 与交付的图数据比对**，不一致 → 判图被篡改或版本漂移，审查无效（确定性脚本使这项成为可能，是本次最强的反造假手段）。
- 判据铁律补一条「未读图 = 审查无效」；强制输出块加「图校验」行；检查点补一条。

## 七、测试与验收

- **历史卦例回归**：17 个真实卦例的 `paipan_result.json` 全部跑通，schema 完整。
- **已知卦例断言**：`26.09.18-水山蹇之地山谦-赛道`——三合申子辰水局成局、独发、初爻辰土日月双空、五爻戌土动化亥水判为「化出我克者」。
- **方向不变量**：每个动爻恰有一个动变关系标签，且与五行方向一致（对齐 `generate_report.py` 现有校验器口径）。
- **确定性**：连跑两次输出字节一致（无时间随机）。
- **交叉一致性**：图与 JSON `patterns` 不得冲突（图可扩展、不可矛盾）。
- **既有测试不回归**：`test_gua_patterns.py` 13 类全过、`check_release_consistency.py` 5 项 PASS。
- 版本升 **v2.1.0**（新增能力、向后兼容），四处版本号同步。

## 八、风险与回滚

主要风险是**图算错会成为新的权威错误源**。三道防线：每条边带 `basis` 可溯源；错误必须修脚本、禁止就地绕过（bug 集中暴露）；17 卦例回归 + 已知卦例断言作门禁。若某类关系机算不可靠（如模糊语义），明确列为「图不覆盖」，不强行机算——宁可留白，不给错值。

## 九、交付顺序

分三段推进，每段独立可验：**① 构建器 + 测试**（可单独验证图正确性）→ **② SKILL.md 集成**（第零步/铁律/第三步）→ **③ 第八步审查 + 报告字段 + 文档版本**。
